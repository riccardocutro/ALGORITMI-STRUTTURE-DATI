\hypertarget{md_Git_autotoc_md7}{}\doxysubsection{Comandi di base per lavorare}\label{md_Git_autotoc_md7}
Git gvi permetterà di salvare il vostro lavoro e manterrà la storia delle varie versioni che avrete creato insieme all\textquotesingle{}indicazione di chi ha effettuato ogni aggiornamento. Segue un elenco dei comandi principali che dovrete utilizzare\+:


\begin{DoxyItemize}
\item {\ttfamily status}\+: mostra lo stato del progetto. File identici all\textquotesingle{}ultima versione salvata non vengono mostrati. File modificati, cancellati, o nuovi vengono visualizzati (con colori diversi se avete abilitato questa opzione).

\hypertarget{md_Git_autotoc_md9}{}\doxysubsection{Branching e Merging con Git}\label{md_Git_autotoc_md9}
Un branch è una linea di sviluppo di un certo repository. Git rende molto semplice lavorare su più branch e effettuare il merge (i.\+e., la fusione) di quanto sviluppato in due branch distinti.

L\textquotesingle{}utilizzo di branch è molto utile per diverse ragioni, ad esempio\+:
\begin{DoxyItemize}
\item permette di non interferire con il lavoro dei colleghi; fino a quando non effettuerò il merge delle mie modifiche sul branch \char`\"{}master\char`\"{} gli altri colleghi potranno continuare a lavorare come se io non avessi modificato nulla;
\item permette di lavorare in modo più \char`\"{}atomico\char`\"{}, la linea di sviluppo principale viene aggiornata solo quando una feature è pronta per essere integrata;
\item permette di organizzare meglio il lavoro; ad esempio molti progetti mantengono un branch \char`\"{}stabile\char`\"{} (di solito chiamato master), uno di sviluppo e uno per le idee che si vogliono esplorare.
\end{DoxyItemize}

Prima di vedere i comandi per creare e modificare i branch è utile capire che Git salva i commit come file contenenti il puntatore (in genere uno solo, ma possono essere più di uno) al commit \char`\"{}genitore\char`\"{} insieme a qualche informazione di contesto (come la mail di chi fa il commit e il messaggio di commit). Un branch è semplicemente un \char`\"{}puntatore\char`\"{} a un commit. In Git, a differenza di altri sistemi di versioning, le operazioni di creazione, modifica e cancellazione di un branch consistono nell\textquotesingle{}aggiornamento di tale puntatore e sono pertanto operazioni poco onerose.

Segue un elenco dei comandi più utili per lavorare proficuamente con i branch.

Quando invocato senza ulteriori argomenti {\ttfamily git branch} riporta la lista dei branch noti\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{\$ git branch}

\end{DoxyCode}


produce un output simile al seguente\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{* branching}
\DoxyCodeLine{  master}
\DoxyCodeLine{  unity\_tests}

\end{DoxyCode}


L\textquotesingle{}output mostrato indica che vi sono attualmente tre branch e che quello in uso è \char`\"{}branching\char`\"{}. Il branch in uso determina il contenuto della working directory. In effetti, nel momento in cui un branch viene attivato (si fa il \char`\"{}checkout\char`\"{} del branch), Git fa sì che la working directory sia aggiornata in modo da riflettere il contenuto dell\textquotesingle{}ultimo commit effettuato sul branch attivato. Se questo non è possibile (ad esempio perché l\textquotesingle{}operazione genera un conflitto che farebbe perdere modifiche non ancora salvate con un commit) Git interrompe l\textquotesingle{}operazione con un messaggio di errore. Un altro effetto di un checkout è di spostare la HEAD in modo tale che punti al branch corrente. Questo implica che da questo momento in poi un commit andrà a modificare il branch corrente piuttosto che quello precedente.

Come menzionato, per lavorare su un particolare branch si usa il comando \char`\"{}checkout\char`\"{} seguito dal nome del branch che si vuole attivare. Ad esempio\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{\$ git checkout master}

\end{DoxyCode}


attiva il branch \textquotesingle{}master\textquotesingle{} e produce un output simile a quanto segue\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{M   Git.md}
\DoxyCodeLine{Switched to branch 'master'}
\DoxyCodeLine{Your branch is up-\/to-\/date with 'origin/master'.}

\end{DoxyCode}


il messaggio ci informa che il checkout ha avuto successo e che però il file {\ttfamily \mbox{\hyperlink{Git_8md}{Git.\+md}}} era stato modificato ed è stato pertanto copiato nella working directory in sostituzione di quello salvato nel branch master. Questo comportamento è utile nei casi si inizi a lavorare su un particolare branch e ci si accorga strada facendo che le modifiche sono più sostanziose di quanto preventivato e che il lavoro merita di proseguire su un branch apposito. In questo caso creando un nuovo branch e facendone il checkout ci ritroveremo con tutte le modifiche già pronte per essere aggiunte al prossimo commit.

Volendo controllare che il checkout abbia avuto successo, potremmo usare nuovamente {\ttfamily git branch} per vedere lo stato dei vari branch. Procedendo con questa operazione otterremo il seguente risultato (l\textquotesingle{}asterisco accanto al branch master indica che, correttamente, il branch attivo non è più {\ttfamily branching})\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{branching}
\DoxyCodeLine{* master}
\DoxyCodeLine{unity\_tests}

\end{DoxyCode}


Supponiamo ora di lavorare su un nuovo progetto su cui sono stati effettuati tre commit. Il comando {\ttfamily git log -\/-\/decorate -\/-\/oneline -\/-\/graph -\/-\/all} mostra la storia del progetto indicando dove is trova la HEAD e quali sono i branch attivi. In particolare, l\textquotesingle{}opzione {\ttfamily -\/-\/graph} indica a git di mostrare il grafo di come si è evoluta la storia del progetto (git log usa per questo una forma di ascii-\/art dove il simbolo {\ttfamily $\ast$} indica un commit e i simboli {\ttfamily /}, {\ttfamily \textbackslash{}} e {\ttfamily $\vert$} sono usati per mostrare le biforcazioni nella storia del progetto). Sul nostro repository di prova il comando restituisce il seguente output\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{* bbcbc23 (HEAD -\/> master) commit 2}
\DoxyCodeLine{* 59b95df commit 1}
\DoxyCodeLine{* 4f49020 initial commit}

\end{DoxyCode}


L\textquotesingle{}output mostra che sono stati effettuati tre commit, che il branch master punta a \char`\"{}commit 2\char`\"{} e che la HEAD è agganciata al branch master. Le stringhe di lettere e numeri accanto alle descrizioni contengono i primi otto caratteri della firma sha1 dei commit\+: in Git ogni commit è identificato dalla sua firma sha1, è possibile effettuare il checkout di un particolare commit indicando tale sigla, es. {\ttfamily git checkout 59b95df} effettuerebbe il checkout del commit 1. Supponiamo ora di voler lavorare su una feature e creiamo un nuovo branch usando il comando\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{git checkout -\/b feature1}

\end{DoxyCode}


Effettuiamo un commit ottenendo la seguente situazione\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{* f252716 (HEAD -\/> feature1) commit 3}
\DoxyCodeLine{* bbcbc23 (master) commit 2}
\DoxyCodeLine{* 59b95df commit 1}
\DoxyCodeLine{* 4f49020 initial commit}

\end{DoxyCode}


{\itshape Nota}\+: il comando {\ttfamily checkout -\/b feature1} combina in un comando unico l\textquotesingle{}effetto dei comandi {\ttfamily git branch feature1} (crea il branch {\ttfamily feature1}) e {\ttfamily git checkout feature1}.

In questo momento il branch master non ha subito ulteriori commit e perciò è collegato in linea diretta con il branch \textquotesingle{}feature1\textquotesingle{}. Nel caso volessimo effettuare il merge di master e feature1 Git semplicemente sposterebbe il puntatore \textquotesingle{}master\textquotesingle{} in modo da farlo puntare al \textquotesingle{}commit 3\textquotesingle{}. Si dice in questo caso che il merge si può fare in modo \textquotesingle{}fast forward\textquotesingle{}.

Invece di effettuare il merge assumiamo invece che ci sia del lavoro da fare su master. Lasciamo in sospeso quanto stiamo facendo su feature1 e Effettuiamo il checkout di master seguito da un commit. Otterremo la seguente situazione\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{* 884d3b5 (HEAD -\/> master) commit 4}
\DoxyCodeLine{| * f252716 (feature1) commit 3}
\DoxyCodeLine{|/}
\DoxyCodeLine{* bbcbc23 commit 2}
\DoxyCodeLine{* 59b95df commit 1}
\DoxyCodeLine{* 4f49020 initial commit}

\end{DoxyCode}


L\textquotesingle{}output mostra che feature1 e master contengono entrambi delle modifiche e che pertanto un merge fast forward non è possibile. Se a questo punto volessimo includere le modifiche apportate in feature1 dentro il branch master potremmo procedere usando il comando {\ttfamily git merge feature1}. Questo comando effettuerà un \textquotesingle{}merge a tre vie\textquotesingle{}. In particolare discenderà nel grafo a partire dal branch corrente (master) e dal branch indicato (feature1) fino a trovare un antenato comune (commit2). A questo punto tenterà di fondere il contenuto di master, di feature1 e del commit 2 e (in caso di successo) creerà un nuovo commit che avrà come genitori sia master che feature1\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{*   7464f65 (HEAD -\/> master) Merge branch 'feature1'}
\DoxyCodeLine{|\(\backslash\)}
\DoxyCodeLine{| * f252716 (feature1) commit 3}
\DoxyCodeLine{* | 884d3b5 commit 4}
\DoxyCodeLine{|/}
\DoxyCodeLine{* bbcbc23 commit 2}
\DoxyCodeLine{* 59b95df commit 1}
\DoxyCodeLine{* 4f49020 initial commit}

\end{DoxyCode}


Si noti che feature1 è fermo al commit3 mentre il branch master è stato spostato per farlo puntare al commit contenente il merge. Questo è corretto, infatti il merge ha incluso in master le modifiche in feature1, mentre feature1 è rimasto invariato. Si noti comunque che a questo punto feature1 è direttamente collegato con master e che quindi un merge feature1 produrrebbe un merge fast forward\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{*   7464f65 (HEAD -\/> feature1, master) Merge branch 'feature1'}
\DoxyCodeLine{|\(\backslash\)}
\DoxyCodeLine{| * f252716 commit 3}
\DoxyCodeLine{* | 884d3b5 commit 4}
\DoxyCodeLine{|/}
\DoxyCodeLine{* bbcbc23 commit 2}
\DoxyCodeLine{* 59b95df commit 1}
\DoxyCodeLine{* 4f49020 initial commit}

\end{DoxyCode}
\hypertarget{md_Git_autotoc_md10}{}\doxysubsection{Risoluzione dei conflitti}\label{md_Git_autotoc_md10}
Se due branch modificano entrambi, in modo differente, la stessa porzione di un file l\textquotesingle{}operazione di merge fallirà segnalando un conflitto. Assumiamo ad esempio che, diversamente da prima, i commit 3 e 4 abbiano introdotto un conflitto su uno dei file del progetto. In particolare assumiamo che gli sviluppatori stessero modificando la funzione \textquotesingle{}swap\textquotesingle{} inizialmente definita come\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{}
\DoxyCodeLine{\textcolor{keywordtype}{void} swap(ArrayList<T> array, \textcolor{keywordtype}{int} p1, \textcolor{keywordtype}{int} p2) \{}
\DoxyCodeLine{  T tmp = array.get(p1);}
\DoxyCodeLine{  array.set(p1, array.get(p2));}
\DoxyCodeLine{  array.set(p2, tmp);}
\DoxyCodeLine{\}}

\end{DoxyCode}


e che nel branch {\ttfamily feature1} lo sviluppatore abbia pensato che il nome delle variabili fosse troppo criptico e abbia deciso quindi di modificarli nel seguente modo\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{}
\DoxyCodeLine{\textcolor{keywordtype}{void} swap(ArrayList<T> array, \textcolor{keywordtype}{int} pointer1, \textcolor{keywordtype}{int} pointer2) \{}
\DoxyCodeLine{  T temporary = array.get(pointer1);}
\DoxyCodeLine{  array.set(pointer1, array.get(pointer2));}
\DoxyCodeLine{  array.set(pointer2, temporary);}
\DoxyCodeLine{\}}

\end{DoxyCode}


mentre nel branch master lo sviluppatore abbia invece pensato che fosse opportuno salvare qualche byte di prezioso spazio disco e abbia quindi eliminato il commento javadoc e modificato la definizione come segue\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{\textcolor{keywordtype}{void} swap(ArrayList<T> a, \textcolor{keywordtype}{int} p, \textcolor{keywordtype}{int} q) \{}
\DoxyCodeLine{  T t = a.get(p);}
\DoxyCodeLine{  a.set(p, array.get(p));}
\DoxyCodeLine{  a.set(p, t);}
\DoxyCodeLine{\}}

\end{DoxyCode}


giustamente Git evita di prendere parte alla diatriba circa quale sia lo stile migliore e pertanto nel momento del merge si rifiuta di completare l\textquotesingle{}operazione emettendo il seguente messaggio\+:


\begin{DoxyCode}{0}
\DoxyCodeLine{Auto-\/merging f1.txt}
\DoxyCodeLine{CONFLICT (content): Merge conflict in f1.txt}
\DoxyCodeLine{Automatic merge failed; fix conflicts and then commit the result.}

\end{DoxyCode}

\DoxyCodeLine{    T t = a.get(p);}
\DoxyCodeLine{    a.set(p, array.get(p));}
\DoxyCodeLine{    a.set(p, t);}
\DoxyCodeLine{=======}
\DoxyCodeLine{  /**}
\DoxyCodeLine{   * Swaps the element at index p1 with the element at index p2}
\DoxyCodeLine{   * @param array the array containing the elements}
\DoxyCodeLine{   * @param pointer1    position of the first element}
\DoxyCodeLine{   * @param pointer2    position of the second element}
\DoxyCodeLine{   */}
\DoxyCodeLine{  void swap(ArrayList<T> array, int pointer1, int pointer2) \{}
\DoxyCodeLine{    T temporary = array.get(pointer1);}
\DoxyCodeLine{    array.set(pointer1, array.get(pointer2));}
\DoxyCodeLine{    array.set(pointer2, temporary);}

\DoxyCodeLine{  \}}

\end{DoxyCode}


Questa marcatura informa l\textquotesingle{}utente che la parte tra {\ttfamily $<$$<$$<$$<$$<$$<$$<$ HEAD} e {\ttfamily =======} è la versione \char`\"{}corrente\char`\"{} (i.\+e., quella presente nel branch in uso), mentre la parte tra {\ttfamily =======} e {\ttfamily $>$$>$$>$$>$$>$$>$$>$ feature1} è la versione presente nel branch {\ttfamily feature1}. Per risolvere il conflitto è necessario modificare il file in questione scegliendo la parte che si vuole mantenere (o effettuando una fusione delle due parti). In questo caso noi decideremo di mantenere la versione nel branch \textquotesingle{}feature1\textquotesingle{} e modificheremo tale porzione del file eliminando le marcature introdotte da Git e tutto ciò che compare nella parte \textquotesingle{}HEAD\textquotesingle{}, a fine lavoro avremo sostituito il testo sopra riportato in modo da leggere\+:

\DoxyCodeLine{ * Swaps the element at index p1 with the element at index p2}

\DoxyCodeLine{  T temporary = array.get(pointer1);}
